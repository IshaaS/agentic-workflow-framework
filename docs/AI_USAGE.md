# AI-assisted development disclosure

AI assistance was used extensively in this project, and the assessment
permitted it. This document records which tools were used, what each one
contributed, what the author did, and how the work was verified. The facts
come from the commit history, the pull requests and the implementation
handoffs produced during development. Items that only the author can confirm
are listed in the [verification checklist](#author-verification-checklist) at
the end, not stated as fact.

## Summary

| Contributor | Role |
|---|---|
| ChatGPT | Requirements analysis, architecture discussion, implementation planning, drafting the sprint specifications, reviewing implementation handoffs, debugging analysis |
| Claude Code (Claude Opus 5.5) | Generated the repository implementation: Python code, tests, CLI, packaging, CI configuration and documentation; ran local tests and Git/GitHub operations |
| Author | Scope and design decisions, review of specifications and handoffs, manual and live testing, pull-request review and merges |
| Anthropic API (runtime) | Optional intent extraction for `agentctl run workflow --request`. This is part of the product, separate from the coding assistant |

## Development process

1. **Requirements:** the assessment requirements were reviewed with ChatGPT
   and split into mandatory features and optional enhancements. The result is
   the [master plan](AGENTIC_WORKFLOW_FRAMEWORK_MASTER_PLAN.md).
2. **Sprints:** the work was divided into seven bounded sprints.
3. **Specification:** before each sprint, the author discussed and refined the
   architecture, contracts, assumptions, boundaries, tests and acceptance
   criteria with ChatGPT. ChatGPT then helped produce a Markdown specification
   for the approved design ([docs/sprints/](sprints/)).
4. **Implementation:** the specification and a short prompt were given to
   Claude Code. Claude Code inspected the existing code, implemented the
   sprint, ran the tests, committed, pushed and opened the pull request.
5. **Handoff and review:**
   - Claude Code wrote an implementation handoff for each sprint.
   - With ChatGPT's help, the author reviewed the handoff, evaluated the
     design decisions, interpreted the test results and identified further
     checks.
   - Follow-up requests went back to Claude Code.
6. **Verification and merge:** the author made the scope decisions, ran manual
   checks of the installed CLI, live weather runs and live Anthropic runs, and
   merged each pull request.
7. **Sprint 6 debugging:** live testing exposed missing `activity` extraction
   (see [debugging lessons](#debugging-lessons)). ChatGPT helped analyse the
   failure and recommend further debugging. Claude Code investigated and
   implemented the fixes, and the author's later live run confirmed them.
8. **Sprint 7 and documentation:** Sprint 7 improved the independent Clothes
   Adviser after a discussion of scope and of its relevance to the assessment.
   A final live Sprint 7 test processed an office/business-casual request
   through Anthropic, generic validation, dynamic planning, all three agents
   and SQLite. This final documentation pass was also carried out by Claude
   Code from the author's instructions.

## Runtime LLM usage

Anthropic is also an optional runtime provider in the product itself:
- **Where:** `agentctl run workflow --request "..."` calls the Anthropic
  Messages API (default model `claude-opus-5-5`, configurable with
  `ANTHROPIC_MODEL`).
- **What it does:** the model extracts a goal and parameters from the request,
  using a catalog built from plugin metadata.
- **What it doesn't do:** it does not choose agents, create workflow steps or
  execute tools. Its answer is validated before the deterministic planner
  runs.
- **Separate from development:** this runtime use has nothing to do with the
  coding assistant used during development.
- **Optional:** structured commands (`--goal`, named workflows) need no
  Anthropic key or SDK. The weather agent still needs network access to
  Open-Meteo unless it is mocked, as it is in the tests.
- **Keys:** API keys are read from the environment, never logged, and not
  stored in the repository.

## Debugging lessons

These are from Sprint 6 live testing, in which the author ran the requests and
Claude Code diagnosed and fixed the problems:

1. **First live run:** "What should I wear for an outdoor walk in Chicago?"
   failed with `missing required input 'activity'`. The original prompt told
   the model to include only values the request literally stated, so it
   omitted `activity`. The prompt was changed to ask for the allowed value
   with the same meaning. A generic, formatting-only canonicalizer was also
   added (`Outdoor walk` → `outdoor_walk`).
2. **Second run:** the model still skipped `activity`. The cause was the
   response schema, not the prompt. Its keys were sorted alphabetically and
   all optional, and structured outputs generate optional keys last, so after
   writing `city` the model could not go back to `activity`. Making every key
   required, in catalog order, with `""` for "not stated", fixed it.
3. **Third run:** succeeded. The model returned `activity=outdoor_walk` and
   left `style` unset, and the planner ran all three agents with live weather
   and the wardrobe.

The lesson: live LLM behaviour has to be checked against the real API.
Scripted tests confirm the deterministic code around the model, but not the
model's behaviour.
