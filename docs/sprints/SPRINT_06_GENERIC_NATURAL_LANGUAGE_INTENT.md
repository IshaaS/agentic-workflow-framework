**Project:** Agentic Workflow Framework  
**Status:** Approved design, implementation specification

**Sprint objective:** Add an **optional, generic Anthropic-powered natural-language entry point** that extracts a *supported goal and validated input parameters* from a user request. The framework must remain fully usable without an Anthropic API key through all existing structured commands.

## 1. Explicit scope and exclusions

### In scope

1. Add **backward-compatible semantic metadata** so independent agent packages can describe supported user-facing goals and expected input parameters.
2. Build a **generic, registry-derived intent catalog**: user-facing goal descriptions plus the required/optional parameters for each goal's relevant dependency chain.
3. Add a **replaceable intent-provider interface** and an **Anthropic implementation** that converts natural-language text into a small structured response (`goal`, `parameters`).
4. Add a **deterministic generic validator** for response shape, registered goal, relevant parameter names, types, allowed values, and missing required inputs; use the existing planner for plan feasibility.
5. Support `agentctl run workflow --request "..."` without breaking named workflows or `--goal` mode.
6. Provide actionable missing-key/provider errors and safe, useful logging; keep output JSON and logs separated.
7. Add offline unit/CLI/integration tests that run in the existing GitHub Actions matrix with **zero secrets and no network calls**.
8. Add concise README updates for the new feature, setup, limitations, and an offline usage path. Preserve the existing AI-use disclosure; final comprehensive README/disclosure polish is scheduled later.

### Out of scope (Sprint 7 or later)

- Adding `office`, `walk`, additional activity aliases, new styles, or changing Clothes Adviser recommendation rules. **Sprint 7 owns clothing-specific enhancements.**
- General free-form garment recommendations generated by the LLM.
- LLM-generated agent plans, dynamic agent/tool execution, agent selection overriding the capability planner, multi-agent reasoning, RAG, chat, persistent session memory, retries, background jobs, or UI.
- Making Anthropic mandatory for core installation, tests, or existing commands.
- Renaming/removing existing manifest fields, CLI commands, entry-point groups, or exception contracts.

**Important limitation:** The current Clothes Adviser has supported activity/style values. In Sprint 6 its *plugin metadata* must truthfully describe the actual accepted values, and natural-language requests for unsupported activities must fail clearly rather than pretending they work. E.g., a request for an unsupported `office` activity is **not** a successful Sprint 6 outcome. Do not bypass restrictions by mapping substantially different activities to arbitrary supported ones. Sprint 7 addresses broader clothing support.

## 3. Behavioral contract

### New supported command

```bash
agentctl run workflow --request "Suggest an outfit for a casual theatre visit in Dallas"
```

The exact words above are illustrative; supported parameter values must match installed plugin metadata. This is the only new public CLI mode.

**Mutually exclusive execution modes:**

- Named: `agentctl run workflow NAME [--input KEY=VALUE ...]`
- Generated: `agentctl run workflow --goal OUTPUT_KEY [--input KEY=VALUE ...]`
- Natural language: `agentctl run workflow --request TEXT` (optionally with explicit `--input KEY=VALUE` overrides, see next subsection)

Require exactly one of `NAME`, `--goal`, `--request`. Keep old modes unmodified. Do not add `agentctl plan` or `agentctl chat`.

### Explicit `--input` in request mode

Allow `--input KEY=VALUE` alongside `--request` as **explicit user-supplied fields**, e.g. `--request "Suggest an outfit for a casual theatre visit" --input city=Dallas`. Merge them **after** LLM extraction. For a duplicate parameter key, the explicit CLI input wins (the user is authoritative), but its value must still pass schema validation. Never silently overwrite the explicit value with an LLM guess. Document this policy and test it. Preserve old `--input` duplicate-rejection behavior.

### Result

Natural language should return exactly the selected goal's value using existing goal-result selection behavior, e.g. the JSON outfit object. Logs/errors stay on stderr; no LLM JSON or secrets on stdout. If the selected goal is already supplied as an input and planner returns an empty plan, retain existing empty-plan semantics.

### Missing key behavior: mandatory

When invoked in **request mode** with no usable `ANTHROPIC_API_KEY`, exit **before calling the LLM or executing any agent**. A helpful example:

```text
agentctl: error: natural-language requests are unavailable: ANTHROPIC_API_KEY is not configured.
Structured commands still work without an Anthropic key:
  agentctl run workflow --goal OUTPUT_KEY --input KEY=VALUE
  agentctl run workflow WORKFLOW_NAME --input KEY=VALUE
Set ANTHROPIC_API_KEY to enable --request.
```

Check the key for nonempty, non-whitespace content. Do not disclose the key value. Use **exit 5** for missing/provider configuration (reuse the existing non-execution error code; document that it now also covers intent-provider configuration). Invalid/expired API credentials must produce a friendly authentication/configuration failure, not a raw SDK traceback. Network/timeouts/rate limits/provider failures should generate controlled failure messages and nonzero status (choose and pin a consistent code, recommended **4** for provider runtime failures). No workflow should be run if intent resolution or validation fails.

**Structured commands must not check the Anthropic key, import Anthropic at module import time, or require the Anthropic SDK to be installed.**

## 4. Semantic metadata: compatible SDK extension

Current `Capability(name, requires, produces)` must continue to construct and behave exactly as before. Add only **optional, defaulted metadata**. One suggested minimal design is below; the coding assistant may make equivalent small improvements if consistent with the invariants.

```python
@dataclass
class InputSpec:
    name: str
    description: str
    value_type: str = "string"    # Sprint 6 may support string only or a small explicit type set
    allowed_values: list[str] | None = None
    # Requiredness is derived from Capability.requires; do not let a flag contradict it.

@dataclass
class GoalSpec:
    output_key: str
    description: str

@dataclass
class Capability:
    name: str
    requires: list[str]
    produces: list[str]
    # Newly appended fields, so all old positional/keyword constructions still work:
    input_specs: list[InputSpec] = field(default_factory=list)
    goals: list[GoalSpec] = field(default_factory=list)
```

Design rules:

- Only goals explicitly advertised as user-facing through `GoalSpec` are shown to the natural-language resolver. Existing `--goal` remains able to target any producible output, whether or not advertised to the LLM.
- `GoalSpec.output_key` must be in the declaring capability's `produces` list. Reject malformed metadata with a clear error.
- `InputSpec.name` must correspond to a declared **required** `requires` key or a declared **optional** input. For optional fields, use an explicit mechanism, such as `optional_inputs: list[str] = field(default_factory=list)` on `Capability`, with matching `InputSpec` entries, so `style` can be described without treating it as mandatory. **Do not require style just because it is listed in metadata.**
- Avoid changing the planner's dependency meaning: `requires` stays mandatory; optional input metadata is only for interpretation/validation and is passed through by the existing orchestrator when supplied.
- Do not add input schemas or user-facing goals to the generic framework as constants. Metadata belongs in individual independent plugin packages.
- Keep metadata dataclasses dependency-light and re-export them where sensible (`agentctl_core.__init__`).
- A plugin with no new intent metadata remains fully functional through `--goal`/named workflows; it simply may not expose a natural-language goal.
- Reject duplicated/conflicting goal definitions or incompatible schema definitions deterministically; don't silently choose a provider.

**Current plugins:** Add user-facing goal metadata only where appropriate (e.g. `outfit` on the shelf-producing capability). Add input descriptions to the relevant weather/clothes capabilities; add the existing supported allowed values for constrained `activity` and `style`. Do not change their underlying `run()` implementations or business rules. Do not advertise `office` or `business_casual` unless the agent already supports them (Sprint 7 will add more).

**Goal description may be separate from input specs** if that simplifies implementation; the requirement is discoverable, truthful semantic metadata tied to plugin-provided capabilities.

## 5. Generic catalog derived from installed plugins

Implement a reusable catalog builder (e.g. `intent_catalog.py`) that reads `AgentRegistry`, **not named application classes**.

For each advertised user-facing output:

1. Resolve its provider from registry capability metadata.
2. Determine the relevant upstream capabilities and mandatory external inputs for *that goal's dependency chain*, not for unrelated installed agents.
3. Collect relevant optional inputs from those same capabilities.
4. Attach descriptions, types, allowed values, and required flags derived from `requires` vs optional declarations.
5. Reject or clearly report incompatible metadata, conflicting parameter definitions, duplicate goal claims, cycles or ambiguous providers. Use/reuse planner exceptions where possible, and **do not duplicate the planner's execution-order algorithm**.

**Implementation guidance:** Reuse `CapabilityPlanner.plan_for_goal()` to determine goal-relevant ordered steps where feasible. To obtain a plan before user values exist, the catalog builder may provide *temporary symbolic placeholders* for declared external fields **strictly for catalog derivation**; these must not be passed to the actual execution or used to make up user input values. Once the plan is known, inspect the relevant steps' `requires`, `produces`, and optional metadata. Keep an explicit test for goals with unrelated plugins installed to ensure unrelated inputs are not requested. If metadata is insufficient to derive a safe catalog, fail clearly rather than guessing.

A catalog record might look like this (illustrative result, **not hardcoded data**):

```json
{
  "goals": [
    {
      "name": "outfit",
      "description": "Choose an outfit from an available wardrobe",
      "parameters": {
        "city": {"type": "string", "description": "City for the forecast", "required": true},
        "activity": {"type": "string", "description": "Supported activity", "required": true,
                     "allowed_values": ["outdoor_walk", "theatre", "casual"]},
        "style": {"type": "string", "description": "Preferred style", "required": false,
                  "allowed_values": ["casual", "formal"]}
      }
    }
  ]
}
```

The validator must **not trust this example** as a source of truth; it reads the actual discovered metadata.

## 6. Generic LLM intent-provider interface and Anthropic adapter

Keep the provider boundary small so tests can inject a fake response without network access.

Illustrative interface:

```python
@dataclass
class ResolvedIntent:
    goal: str
    parameters: dict[str, Any]

class IntentProvider(Protocol):
    def resolve(self, request: str, catalog: IntentCatalog) -> ResolvedIntent: ...
```

**Anthropic adapter:**

- Implement in an isolated module, such as `agentctl_core/providers/anthropic.py` (or separate optional provider package if simpler), lazily import `anthropic` only in request mode.
- Declare SDK in an optional package extra, e.g. `pip install -e './framework[llm]'`. Ensure `pip install -e './framework[dev]'` and ordinary CLI usage still work with no Anthropic package or key.
- Read `ANTHROPIC_API_KEY` from environment. Use a documented model configuration (`ANTHROPIC_MODEL` optional), with a known-valid default *verified during implementation* rather than an assumed/stale model identifier.
- Use Anthropic's current supported API and its available structured-output mechanism when appropriate. Verify the actual installed SDK/API surface; do not assume that a fabricated model or method exists. Parse defensively and accept only a single `goal` string plus an object of parameters.
- Keep system instruction generic: choose only advertised user-facing goals, extract only catalog-declared parameters, respect enum values, do not invent missing user details or unsupported actions, produce structured JSON. Treat request text and plugin-provided descriptions as data, not executable instructions.
- Use low-variance settings and small output limits suitable for extraction. No chain-of-thought requests or unconstrained agent plans.
- Inject/mock the provider in tests. No Anthropic key or paid calls in GitHub Actions.
- Catch missing SDK, missing key, authentication, timeout, rate limiting, malformed response, and transport failures; turn them into concise typed errors at the provider boundary. Never log keys, bearer headers, full raw provider payloads, or user secrets.
- Don't silently fallback from an invalid natural-language request to arbitrary hardcoded values.

If the model outputs uncertainty, an unsupported request, or incomplete information, return a controlled error/validation outcome; **this is a one-shot CLI**, not interactive chat. A single retry for malformed provider output is optional, not required; if used, it must be bounded and covered by tests.

## 7. Deterministic Generic Validator

The validator accepts the catalog and the model-proposed `ResolvedIntent` (plus explicit CLI overrides) and returns a validated `(goal, inputs)` or a structured failure. It must be completely domain-neutral.

Required checks, in order:

1. **Response structure:** valid object; nonempty string `goal`; `parameters` is a mapping with string keys; reject unexpected top-level fields if using a strict response contract.
2. **Supported goal:** selected goal exists in the *advertised* user-facing catalog, not merely an invented string.
3. **Allowed parameters:** every supplied key is declared for the selected goal's dependency chain. Reject unknown keys; do **not** silently ignore LLM hallucinations or misspellings.
4. **Type checks:** strict validation of declared types; do not silently coerce arbitrary values (e.g. number to string). Required strings must be nonempty after trimming. Keep types minimal and test them.
5. **Constrained values:** enforce declared `allowed_values` exactly (or a documented normalization policy; no fuzzy/unannounced semantic remapping). Optional inputs such as `style` stay optional.
6. **Required external fields:** identify only inputs needed for the chosen goal's plan. Report missing inputs by their field names. Do not demand inputs of unrelated installed plugins or guess missing city/file paths.
7. **Plan feasibility:** call the *existing* `CapabilityPlanner.plan_for_goal()` with validated inputs and documented external-input policy; let it detect ambiguity, cycles, collisions, and missing capabilities. Do not reimplement planning.

Return messages such as:

```text
agentctl: error: missing required input 'city' for goal 'outfit'; supply --input city=VALUE
agentctl: error: unsupported natural-language goal 'flight_booking' (available: outfit)
agentctl: error: parameter 'style' must be one of: casual, formal
agentctl: error: unknown parameter 'fashion_score' for selected goal 'outfit'
```

**No workflow execution** after any validation/planning error. **Explicit CLI overrides** must be validated under the same schema and take precedence over LLM-proposed values. Do not retry or reinterpret invalid values by guessing.

## 8. CLI integration and logging

Modify only the minimal existing CLI parsing/dispatch needed:

```bash
agentctl run workflow --request "What should I wear for a casual theatre visit in Dallas?"
agentctl run workflow --request "Suggest a casual theatre outfit" --input city=Dallas
```

Dispatch request mode roughly as follows:

```text
parse args + ensure exactly one of NAME / --goal / --request
if --request:
    validate request text nonempty
    check ANTHROPIC_API_KEY and optional SDK availability (friendly exit 5)
    discover installed agents
    build generic user-facing goal catalog
    call intent provider to get goal + parameters
    merge explicitly provided --input values (explicit input wins)
    validate all parameters, required fields, supported goal
    invoke existing CapabilityPlanner.plan_for_goal(goal, inputs, external_inputs)
    create normal RuntimeContext with unique IDs
    invoke existing SequentialOrchestrator.execute(plan, context)
    print selected goal's JSON result to stdout
else:
    use the *unchanged* named/--goal route
```

Maintain existing error codes `0/2/3/4/5` and existing stdout/stderr expectations. Suggested classification: syntax/empty request → 2; unsupported or invalid intent/parameter/planning → 3; provider runtime or workflow execution failure → 4; missing SDK/key/authentication/configuration → 5. Pin codes in tests and document if extending the meaning of code 5.

For request mode, log safe milestones to `agentctl` stderr logger: request mode entered, catalog built (goal count), intent validated (goal identifier, not whole user text), workflow ID, capability-step execution, timing. Avoid printing raw prompts or full user-supplied text unless explicitly opted in (not part of Sprint 6). Do not print access tokens or secrets. Preserve no-handler-on-import behavior and restore logging handlers after `main()`.

Do not change the CLI's existing named/goal path behavior for missing Anthropic SDK/key.
